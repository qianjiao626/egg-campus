# 蛋蛋校园生产数据与实时化改造设计

## 目标

在不整体重写现有页面、不删除现有 REST 接口、不启用商城前端的前提下，清除生产环境演示数据，修复任务、注册、会话、个人资料和邀请码链路，并用 WebSocket 事件通知增强任务、盲盒、吐槽树洞与排行榜的实时更新。

## 确认范围

- 生产数据库仅保留 `蛋总-敦敦`、`蛋总-千焦`、`教练` 三个账号。
- `蛋总-敦敦`、`蛋总-千焦` 保持管理员身份；`教练` 保持普通用户身份。
- 删除其余账号及其全部关联数据。用户已明确授权不创建生产备份。
- 三个保留账号的可用蛋蛋币重置为 `100`，冻结余额重置为 `0`，流水仅保留一条 `register_bonus`，展示文案为“初次上线 +100 蛋蛋币”。
- 生产前端删除假账号、假任务、假榜单、假树洞、假邀请码历史和 Demo 流水；自动化测试目录中的 mock、fixture 和测试账号构造器保留。
- 固定标题、按钮、字段说明、空状态提示和页面结构可以保留；用户、任务、榜单、反馈、盲盒、邀请状态等业务数据必须来自后端。
- 商城前端继续通过现有开关隐藏；商城代码与未执行迁移保留。本轮不执行商城迁移。
- 不接触“航线”项目或 Supabase。
- 手机号登录和短信配置继续取消；昵称登录保留，邮箱为可选联系方式，填写邮箱不强制验证码。

## 实施策略

采用分阶段垂直改造：先建立数据模型和契约测试，再修复任务及认证链路，随后清理生产前端静态业务数据，最后接入 WebSocket、部署到独立测试库并上线。每个阶段保持 REST 可用并运行现有测试，避免一次性大改导致问题难以定位。

## 数据模型

### 任务技能与可见性

`Task` 新增可空字段 `skillCategory` 与 `skillSubcategory`。每个任务最多保存一个技能大类和一个技能子类，沿用现有前端选择器。创建、编辑和查询均读写这两个字段。

任务状态由后端控制可见性：

| 状态 | 发布者 | 具备任务审核权限的管理员 | 其他合法登录用户 |
| --- | --- | --- | --- |
| `draft` | 可见 | 不可见 | 不可见 |
| `pending_review` | 可见 | 可见 | 不可见 |
| `needs_revision` / `rejected` | 可见 | 可见 | 不可见 |
| `approved` | 可见 | 可见 | 可见 |
| `completed` / `cancelled` | 按本人任务或已接取关系可见 | 可管理 | 不进入公开广场 |

新增统一公开任务接口和管理员审核队列接口，前端不再对返回的任务做权限过滤。任务序列化结果包含 `activeClaimCount` 和当前用户的 `claimStatus`。人数来自 `TaskClaim` 的真实聚合，不允许前端本地累加。

### 邀请关系

新增邀请关系记录，包含邀请人、被邀请人、邀请码快照、创建时间、奖励时间和触发任务。被邀请人与关系一对一，数据库唯一约束阻止重复绑定；邀请人和被邀请人不能相同。

注册时可提交邀请码。服务端验证邀请码存在、对应账号有效且不是本人，然后在注册事务内创建关系。被邀请人首次任务审核通过时，在同一事务中锁定邀请关系，向邀请人发放 `20` 蛋蛋币，写入带唯一幂等键的流水并记录奖励时间。后续任务审核不会重复奖励。

### 生产清理

提供只能由命令行显式执行的一次性维护脚本，不暴露 HTTP 路由。脚本要求传入生产确认值和三个昵称白名单，并在单个数据库事务内：

1. 校验三个账号均存在、身份符合要求且白名单恰好为三个账号。
2. 删除其他账号；依靠已确认的级联规则删除个人业务数据，对 `Restrict` 或 `SetNull` 关系显式按依赖顺序处理。
3. 删除三个账号现有蛋蛋币流水。
4. 将三个账号账户设置为可用 `100`、冻结 `0`，并各写入一条 `register_bonus` 流水。
5. 清理与已删除用户相关且未被外键覆盖的审计或文件数据。
6. 输出受影响行数和最终三个账号的余额，不输出密码或连接串。

脚本在测试数据库先执行并验证。按用户明确授权，生产执行前不创建备份；脚本任何校验失败则事务回滚。

## 后端接口

### 任务

- `GET /api/tasks`: 仅返回 `approved` 的公开任务，要求合法登录。
- `GET /api/admin/tasks/review-queue`: 仅具备任务审核权限者访问，返回待审核及待修改任务。
- `GET /api/tasks/mine`: 仅返回当前用户发布的任务。
- `GET /api/tasks/claimed`: 返回当前用户真实接取记录和任务快照。
- `POST /api/tasks`: 写入技能大类/子类并进入待审核。
- `PATCH /api/tasks/:id`: 仅发布者编辑草稿或待修改任务，保存技能字段并重新提交审核。
- `POST /api/tasks/:id/claim` 与放弃接口：在事务内写入 `TaskClaim`、处理蛋蛋币冻结/返还，并返回聚合后的真实人数。
- `PATCH /api/tasks/:id/review`: 审核通过时处理任务奖励冻结、经验奖励、邀请码首次奖励和实时事件。

所有权限决策依赖服务端实时 RBAC 查询，不信任 JWT 中的 `role` 字段。

### 注册与会话

- 昵称长度 `2-50`，密码长度 `8-128`，年龄为 `13-100` 整数，邮箱存在时必须格式合法。
- 前端先校验；非法输入不发请求。
- 后端将 Zod 参数异常、重复昵称/邮箱、邀请码错误和数据库异常映射为稳定中文业务提示，不返回堆栈。
- 登录继续使用短期 access token 与 HttpOnly refresh cookie。页面刷新或重新打开时，通过 refresh 和 `/api/users/me` 恢复状态，不使用 `sessionStorage` 或 `localStorage` 保存凭证。

### 邀请码界面

后端返回当前用户邀请码、邀请链接、已邀请数量、已奖励数量、累计奖励及邀请历史。前端保留现有 UI，数据全部来自接口；复制和填写操作展示明确成功、无效、重复、自邀和已绑定提示。

## WebSocket

服务端新增 `@fastify/websocket` 与 `ws`，复用现有 Fastify 进程。连接路径为 `/api/realtime`，使用短期 access token 完成握手认证，并在连接后按用户 ID 和实时 RBAC 权限建立订阅上下文。

WebSocket 只发送事件，不承载业务写入或完整业务对象。事件信封固定包含：

```json
{
  "type": "task.updated",
  "resourceId": "123",
  "scope": "public",
  "occurredAt": "2026-08-27T00:00:00.000Z"
}
```

事件范围：

- 任务：发布、编辑、审核、接取、放弃、提交、完成。
- 盲盒：投放、抽取、试题通过、会话开启、声望变动。
- 吐槽树洞：发布、点赞、回复、采纳。
- 排行榜：经验、声望或蛋蛋币变化。

公共事件只发给合法登录用户；审核队列事件只发给具有任务审核权限的管理员；审核结果、盲盒会话和个人资产变化只发给相关用户。客户端收到事件后调用现有 REST 接口刷新对应区域。

前端提供一个全局实时开关。连接采用有限指数退避重连；连续失败后停止刷屏并调用 REST 全量刷新。进入页面时注册处理器，离开页面时注销；同一事件处理器不得重复注册。

Nginx `/dd/api/realtime` 配置 Upgrade/Connection 头并保持与现有 `/dd/api/` 代理前缀一致。

## 前端改造

- 保留现有主站 UI、按钮和布局，禁止整体重写。
- 删除静态任务卡、榜单行、个人资料示例、Demo 蛋蛋币/经验流水、Demo 树洞数组和假邀请码历史。
- 各列表容器初始为空并显示固定空状态，由 REST 返回数据后渲染。
- 个人页彻底删除中部 `profile-head` 用户名头像长条 DOM；MPI 蛋蛋小人保留。用户名和学校信息移动到个人页现有顶部栏右侧，不新增嵌套卡片。
- 任务人数、接取标记、技能字段、个人资料、排行榜和邀请历史均以服务端返回值为准。
- 盲盒继续作为主站内容组件，不恢复独立外壳。

## 测试与环境隔离

独立测试会话使用 CVM 同一 MySQL 服务上的 `dandan_campus_test`，不得写入生产库。测试环境有独立 `DATABASE_URL`、会话密钥和进程/端口，生产 Nginx 不代理测试服务。

每轮测试文档写入 `docs/online-test-reports/`，包含：测试时间、用例项、预期结果、实际结果、是否通过、问题简述。覆盖动态效果、注册、登录持久化、任务、盲盒、吐槽树洞、排行榜、个人页、邀请码、WebSocket 和数据持久化。

测试层级：

1. 领域单元测试：任务可见性、邀请奖励幂等、事件路由、清理白名单。
2. Fastify 契约测试：认证、权限、输入错误、持久化和 WebSocket 隔离。
3. 前端契约测试：不存在生产 Demo 数据，列表仅从接口渲染，实时监听正确销毁。
4. 独立测试库集成测试：刷新后接取数和技能字段不丢失，邀请奖励只结算一次。
5. 线上无副作用冒烟：健康检查、静态资源、登录恢复和 WebSocket 握手。

## 部署与验收

- 本机运行全部测试和 TypeScript 构建；前端为静态包时本机生成部署产物。
- 使用指定磁盘私钥直接 SSH/SCP，不使用 ssh-agent、ssh-add 或密码登录。
- 增量上传，不删除服务器 `node_modules`；新增依赖后在服务器执行一次依赖更新。
- 先部署测试环境并执行迁移、回归和清理脚本演练，再部署生产应用与非商城迁移。
- 检查 Nginx 配置、PM2 日志、MySQL 错误、健康接口、REST 和 WebSocket；PM2 `online` 不视为业务验收完成。
- 生产部署验证后执行已授权的数据清理事务，并核验数据库仅有三个账号、余额均为 `100`、每人仅一条初次上线流水。

验收完成时：现有自动化测试全部通过；新增用例通过；页面无演示业务数据；任务权限与持久化正确；注册和会话稳定；邀请奖励幂等；WebSocket 断线时 REST 降级可用；商城仍隐藏；航线项目无变化。
