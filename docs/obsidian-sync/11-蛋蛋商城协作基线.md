## 已统一的决定

- 商城不建立第二套发布者授权表；商品发布者是统一 RBAC 的预置角色。
- 只有两个固定管理员能授予、续期、永久化或撤销商品发布者角色。
- 商城运营权限按商品、库存、订单、发货、退款、评价和审计拆分，服务端逐项校验。
- `Product.publisherId` 只表示资源归属，不能证明用户当前仍有发布权限。
- 用户失去某一个角色不等于失去发布能力；必须在其所有有效角色均不再提供发布权限后，才下架其未售罄商品。
- 商城图片目录和反馈私密附件目录必须隔离，不能把反馈附件暴露为静态资源。

## 实施顺序

1. 当前平台任务先落地规范化 RBAC、首次改密、个人资料、任务中心与反馈基础。
2. 商城任务可先编写商城专属的纯业务 helper、输入 schema 和测试，不修改共享入口。
3. RBAC 接口稳定后，商城增加数据模型、商品/购物车/订单 API 和细粒度权限检查。
4. 最后由单一任务串行修改 `app.ts`、`api-client.js` 和 `growth-school.html`，再做全量回归。

## 文件所有权

- 平台任务：`server/src/authorization.ts`、RBAC/资料/反馈相关测试、共享 Prisma RBAC 模型和共享权限目录。
- 商城任务：`server/src/shop.ts`、`server/tests/shop-*.test.ts`、商城专属文档。
- 串行交接文件：`server/prisma/schema.prisma`、`server/src/app.ts`、`backend-handoff-package/api-client.js`、`backend-handoff-package/growth-school.html`。

## 安全与部署

- 不触碰“航线”及其 Supabase。
- 不在文档、Git、日志或任务消息中记录密码、数据库连接串、JWT 或腾讯云密钥。
- 生产部署继续暂停；完成全量测试、本机构建、Prisma 校验、前端语法检查和公网 smoke 后再发布。

## 本次经验

- 不要因为某个模块需要一种“身份”就立即增加专用授权表；先判断它是否属于全站权限体系。
- 多角色并集下，权限到期后的业务清理必须判断“最终有效能力”，不能只监听某一条授权记录。
- 多任务共享同一工作树时，文件所有权和串行交接比口头约定更可靠。
